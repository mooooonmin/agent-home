# 0006. 커밋 제목 형식은 검사로 강제하고 공통 규칙의 커밋 절은 줄인다

- 상태: 채택
- 날짜: 2026-11-05

## 배경

[0004](0004-keep-always-loaded-rules-under-200-lines.md) 이후 새 프로젝트 `AGENTS.md`가 다시 198~200줄이 되었습니다. 구성은 저장소 안내 42~44줄 + 공통 규칙 156줄입니다. 이 줄 수는 언어 5개 × 번역 여부로 프로젝트를 만들어 직접 셌습니다.

이대로는 자리표시를 실제 명령·구조로 채우는 순간 200줄을 넘습니다. 그러면 저장소 검사가 실패하고, 끝내기 전 훅과 CI가 막습니다.

공통 규칙에서 가장 긴 부분은 커밋 메시지와 본문 양식이었습니다(17 + 23 = 40줄). 커밋할 때만 필요한 내용입니다. 그중 제목 형식은 기계로 확인할 수 있습니다.

## 결정

- `repo_checks.py`가 커밋 제목을 검사합니다.
  - 형식: `type(scope): 설명`이어야 합니다.
  - 설명: "수정", "개선", "작업 완료"뿐이면 실패입니다.
  - 기본 범위는 아직 어느 원격에도 올리지 않은 커밋입니다. 끝내기 전 훅과 `git push` 전 훅이 이 범위를 봅니다.
  - 셸 명령 전 훅은 `git commit -m "제목"`처럼 명령에 그대로 적힌 제목도 커밋 전에 봅니다.
  - CI는 PR이면 `origin/<기준 브랜치>..HEAD`를 봅니다.
  - 병합 커밋과 git이 만든 `Revert "..."`·`Reapply "..."` 커밋은 건너뜁니다.
- 공통 규칙의 커밋 절은 항목만 남깁니다(48줄 → 15줄). 본문 양식 코드 블록을 지우고 항목 이름을 문장으로 적습니다.
- 새 프로젝트 `AGENTS.md`가 180줄을 넘으면 `test_new_project.py`가 실패합니다. 200줄 한도 안에서 저장소 안내를 채울 여유 20줄을 지키기 위해서입니다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 200줄 한도를 경고로 낮추기 | 바꿀 것이 적음 | Claude Code 권장 크기를 넘는 파일이 그대로 남음 |
| 커밋 절을 스킬로 옮기기 | 커밋할 때만 읽힘 | 스킬이 저절로 불린다는 보장이 없어, 규칙이 빠질 수 있음 |
| git `commit-msg` 훅 | 커밋하는 순간 막음 | `core.hooksPath` 설정이 clone에 따라오지 않아 클라우드 세션마다 따로 켜야 함 |
| 셸 명령 전 훅에서 모든 형태의 커밋 메시지 읽기 | 커밋 전에 항상 막음 | `-F`, heredoc, `$(cat ...)`은 명령만으로 내용을 알 수 없음. 그래서 명령에 그대로 적힌 `-m` 제목만 읽고, 나머지는 푸시 전 검사에 맡김 |

## 결과

- claude-home `AGENTS.md`는 198줄에서 165줄이 되었습니다.
- 새 프로젝트 `AGENTS.md`는 165~167줄이 되었습니다(공통 규칙 123줄). 저장소 안내를 채울 여유는 33~35줄입니다.
- 훅이 놓치는 경우가 하나 남습니다. 제목을 heredoc·`$(...)`·파일로 주면서, 커밋과 푸시를 한 명령(`git commit ... && git push`)으로 하는 경우입니다. 이때는 PR의 CI에서 잡힙니다.
- 이미 올린 커밋의 제목을 고치려면 작업 브랜치의 기록을 다시 써야 합니다(`docs/setup.md`의 문제 해결).
- 검사는 형식만 봅니다. 설명이 한국어인지, 무엇이 바뀌었는지 잘 드러나는지는 규칙 문장과 리뷰에 맡깁니다.
