기록할 것: $ARGUMENTS

`$ARGUMENTS`가 비어 있거나 그대로 보이면(Codex 등) 이번 대화에서 해결한 문제를 대상으로 합니다. 해결한 것이 여러 개면 무엇을 기록할지 묻습니다.

대상 저장소: `mooooonmin/Issue_archive` (공개). 해결한 문제와 명령어·설정 레시피를 이슈 하나에 하나씩 모으고, 라벨별 목차가 README에 자동으로 만들어집니다.

## 언제 쓰나

- 사용자가 "아카이브해줘", "이슈로 남겨줘"라고 할 때
- 대화에서 다시 찾아볼 만한 문제를 해결했다면, 작업을 마칠 때 "Issue_archive에 남길까요?"라고 **한 번만 제안**합니다. 사용자가 원하지 않으면 다시 묻지 않습니다.

## 순서

1. **중복 확인**: 핵심 키워드로 이미 있는 이슈를 찾습니다. 비슷한 것이 있으면 새로 만들지 않고, 그 이슈에 내용을 더할지 묻습니다.
   ```bash
   gh issue list -R mooooonmin/Issue_archive --state all --search "<키워드>"
   ```
2. **분류 고르기**: 저장소 라벨에서 하나를 고릅니다. `bug`, `documentation` 같은 GitHub 기본 라벨은 쓰지 않습니다. 맞는 분류가 없으면 `ETC`를 쓰거나, 새 라벨을 만들지 사용자에게 묻습니다.
   ```bash
   gh label list -R mooooonmin/Issue_archive
   ```
3. **초안 쓰기**: 아래 형식으로 씁니다. 제목과 `###` 머리글은 이슈 폼과 같아야 라벨 자동 적용과 목차가 맞게 동작합니다.
   - 제목: `[분류] 핵심 키워드`. 나중에 검색할 낱말을 앞에 둡니다. 예: `[Windows] 포트를 쓰는 프로세스 찾아 종료`
   - 본문:
     ````markdown
     ### 분류

     Windows

     ### 환경

     Windows 11, PowerShell 7

     ### 상황 / 목적

     (어떤 문제였는지, 무엇을 하려 했는지. 오류 메시지가 있으면 그대로)

     ### 해결 방법

     (실제로 효과가 있었던 순서와 명령. 코드 블록에는 언어를 적습니다: ```powershell, ```bash)

     ### 참고

     (참고한 공식 문서 링크. 없으면 _No response_)
     ````
   - 이번 대화에서 **실제로 실행해 확인한 것만** 해결 방법에 적습니다. 시도했지만 안 된 방법은 필요하면 "안 된 방법"으로 따로 적고, 확인하지 못한 단계는 "미확인"이라고 밝힙니다.
4. **공개 전 점검**: 공개 저장소라서 다음을 지우거나 일반화합니다.
   - 비밀값: 토큰, API 키, 비밀번호, 개인 키, 접속 정보
   - 내 환경 정보: 사용자 이름이 든 경로(`C:\Users\<이름>` → `%USERPROFILE%`, `/home/<이름>` → `~`), 내부 IP·호스트 이름
   - 업무 정보: 업무 저장소(saint-*, sws-*)나 회사·고객사 내부 내용은 옮기지 않습니다. 일반적인 해결법만 남길 수 있으면 그렇게 하고, 아니면 기록하지 않겠다고 알립니다.
5. **확인받기**: 제목, 라벨, 본문 전체를 보여 주고 올려도 되는지 묻습니다. 확인 없이 올리지 않습니다.
6. **등록**: 본문을 저장소 밖 임시 파일에 쓰고 올립니다. 정리가 끝난 메모이므로 바로 닫습니다(열어 두면 목차에 `(open)`으로 표시됨). 사용자가 아직 작성 중이라고 하면 열어 둡니다.
   ```bash
   gh issue create -R mooooonmin/Issue_archive --title "<제목>" --label "<분류>" --body-file <임시 파일>
   gh issue close <번호> -R mooooonmin/Issue_archive
   ```
7. **알리기**: 이슈 주소를 알려 주고 임시 파일을 지웁니다. README 목차는 GitHub Actions가 1분 안팎으로 갱신합니다.
