# 커밋과 PR 규칙

## 커밋 메시지

[Conventional Commits](https://www.conventionalcommits.org/ko/) 형식에 한국어 설명을 씁니다.

```
<type>(<scope>): <한국어 설명>
```

- type: `feat`, `fix`, `docs`, `style`(포맷만 변경), `refactor`, `test`, `chore`, `build`, `ci`
- 번역 저장소는 `docs(ko)`를 씁니다.
  - 예: `docs(ko): 9장 오류 처리 번역`
  - 예: `docs(ko): README를 장별 목차로 작성`
- 한 커밋에는 한 가지 일만 담습니다(번역은 보통 장 하나 = 커밋 하나).
- 설명은 "~ 번역", "~ 추가", "~ 수정"처럼 명사형으로 끝냅니다.
- 제목에는 무엇이 어떻게 바뀌었는지 적습니다. "수정", "개선", "작업 완료"처럼 결과를 알 수 없는 제목은 쓰지 않습니다.
- 커밋 전에 staged diff를 다시 보고, 대화 과정이 아니라 **최종 변경**을 설명합니다.

## 커밋 본문

번역 한 장, 오타 수정처럼 작은 커밋은 제목만으로 충분합니다. 그 외에는 본문을 씁니다. 길이는 변경 크기에 맞추고, 짧으면 제목(`변경 이유:` 등) 없이 문장으로 써도 됩니다.

```text
type(scope): 구체적인 변경 결과

변경 이유:
- <해결하려는 문제나 요구사항>

변경 내용:
- <주요 동작·구조 변경, 필요하면 변경 전후>

검증:
- <실제로 실행한 명령과 결과, 못 한 확인과 그 이유>

문서:
- <고친 문서, 또는 문서에 영향이 없는 이유>
```

- 호환성이 깨지거나 설정·마이그레이션이 필요하면 `호환성:` 항목을 더합니다.
- 확인한 사실만 적습니다. 돌리지 않은 테스트를 통과했다고 쓰지 않습니다.

## 브랜치와 PR

- 기본 브랜치에 바로 커밋하지 말고 작업 브랜치를 만듭니다. 예: `translate/ch09`, `fix/broken-links`
- PR 본문은 `templates/pr-body.md`를 따릅니다.
- 클라우드 세션에서 만든 PR은 내가 직접 확인하고 병합합니다. 자동 병합은 켜지 않습니다.
