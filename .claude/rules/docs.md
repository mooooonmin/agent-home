# 문서 관리 규칙

문서는 코드와 함께 바뀌어야 최신으로 유지됩니다. 나중에 몰아서 고치지 않습니다.

## 주제 하나, 담당 문서 하나

- 주제마다 자세한 내용을 관리하는 **담당 문서**를 하나만 둡니다. 명령어, 설정값, 계약(API·데이터 형식)은 담당 문서에만 적습니다.
- README, CLAUDE.md 같은 안내 문서에는 요약과 링크만 둡니다. 같은 내용을 여러 곳에 복사하지 않습니다.
- 목차 문서를 새로 늘리기보다 기존 목차에 합칩니다.

## 폴더마다 짧은 README

역할이 분명한 최상위 폴더(예: `scripts/`, `tools/`, 계층·모듈 폴더)에는 짧은 `README.md`를 둡니다. 폴더에 들어온 사람이나 AI가 바로 맥락을 잡게 하기 위함입니다. 템플릿: `templates/docs/folder-README.md`

- 이 폴더의 **책임** (한두 문장)
- 파일이나 하위 폴더별 용도 (표)
- **의존하면 안 되는 것** (계층 폴더라면)
- 바꾼 뒤 돌릴 **검증 명령**

3~20줄로 짧게 쓰고, 자세한 설명은 담당 문서로 링크합니다. 폴더 구성이 바뀌면 같은 커밋에서 고칩니다.

## 문서를 검토해야 작업이 끝난다

코드를 바꿨으면, 끝내기 전에 영향을 받는 담당 문서를 찾아 **같은 커밋**에서 고칩니다. 사용자가 따로 요청하지 않아도 합니다.

| 바꾼 것 | 고칠 문서 |
|---|---|
| 설치·실행 방법, 환경 변수, 필요한 도구 | `README.md`의 시작하기 |
| 공개 API, CLI 옵션, 설정 키, 데이터 형식 | `docs/`의 담당 문서, 코드의 문서 주석 |
| 폴더 구조, 주요 모듈 | `README.md`의 구조 설명, `CLAUDE.md` |
| 큰 설계 결정 | 새 ADR (`docs/adr/`) |
| 사용자에게 보이는 변화 | `CHANGELOG.md`의 `[Unreleased]` |
| 계획한 작업의 진행 | `docs/exec-plans/`의 해당 계획 |

- 필요한 문서 수정이 남아 있으면 작업을 완료로 보고하지 않습니다.
- 링크 검사 같은 자동 검사 통과가 내용 검토를 대신하지 않습니다. 문서 내용을 실제 코드와 대조합니다.
- 완료 보고에는 **고친 문서**를 적습니다. 고칠 필요가 없었다면 동작과 계약이 그대로인 이유를 한 줄로 적습니다.
- 검토했다는 걸 보여 주려고 불필요한 수정을 하지 않습니다.

## 문서 구성

새 프로젝트는 다음 구성으로 시작합니다. claude-home의 `/new-project`(`scripts/new-project.ps1`)가 이 구성을 만들어 줍니다. 템플릿: `templates/docs/`

- `README.md`: 무엇인지, 시작하기(설치·실행·테스트 명령), 구조, 문서 링크
- `CLAUDE.md`: 작업별로 먼저 읽을 문서, 빌드·테스트 명령, 이 저장소만의 규칙. 템플릿: `templates/CLAUDE.project.md`
- `docs/adr/NNNN-제목.md`: 설계 결정 기록. 번호는 이어서 붙이고, 결정이 바뀌면 지우지 말고 새 ADR을 만든 뒤 예전 ADR의 상태를 "대체됨"으로 바꿉니다.
- `CHANGELOG.md`: [Keep a Changelog](https://keepachangelog.com/ko/1.1.0/) 형식
- `docs/exec-plans/` (여러 세션에 걸친 작업이 있을 때만): 실행 계획과 개선 목록

## 실행 계획

여러 세션에 걸치거나 클라우드에 맡길 큰 작업은 계획을 저장소에 남깁니다. 다음 세션이 계획 파일만 읽고 이어서 할 수 있게 합니다.

- 진행 중인 계획은 `docs/exec-plans/active/`, 끝난 계획은 `completed/`로 옮기고 목록(`docs/exec-plans/README.md`)을 고칩니다.
- 계획에는 목표, 범위(하는 것/안 하는 것), 단계, 완료 조건, 검증 방법, 남은 문제를 적습니다. 매일의 작업 일지나 로그는 넣지 않습니다.
- 끝낼 때는 최종 커밋과 검증 결과를 연결합니다. "코드 완료"와 "배포·동작 확인"을 구분합니다.
- 당장 하지 않을 개선 후보는 `tech-debt-tracker.md`에 ID, 근거, 완료 조건과 함께 적습니다. 이 목록은 일정이 아니라 후보입니다.
- 빈 계획 파일이나 빈 목록을 미리 만들지 않습니다.

## 문서 쓰는 법

- 결과와 사용법을 먼저, 배경 설명은 뒤에 씁니다.
- 명령어는 복사해서 바로 실행할 수 있게 코드 블록으로 씁니다.
- 주장에는 근거(코드 경로, 테스트, 커밋)를 링크합니다. 확인하지 못한 것은 "미확인"으로 표시합니다.
- 날짜·버전처럼 낡기 쉬운 정보는 꼭 필요할 때만 적습니다.

## 자동 점검

- CI에서 깨진 내부 링크·이미지·앵커를 막습니다(`repo_checks.py`에 포함). 템플릿: `templates/ci/`
- 문서가 코드와 어긋났는지는 `/update-docs`로 점검합니다.
